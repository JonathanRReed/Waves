# Waves 1.7.1 release design

Date: 2026-09-04
Target: version 1.7.1, build 19
Branch: `codex/waves-1.7.1`

## Purpose

Waves 1.7.1 is a maintenance, security, and performance release. It will
adjudicate every open pull request, repair the valid findings without importing
unsafe implementations, audit the whole application, qualify for the Half
Bounce Club under an honest interaction test, and complete the signed public
release pipeline.

The current public release is 1.7.0 build 16. A Wave Link test branch and the
Golden Gate Mac mini already carry an unpublished build 18. Build 19 prevents
Sparkle from treating the new release as older than a known test build.

## Success criteria

The release is complete only when all of these statements are true:

1. Every open Waves pull request has an evidence-backed disposition.
2. No validated critical or high security finding remains open. Every relevant
   medium finding is fixed, and every low finding has a recorded disposition.
3. The shared quality gate, focused regression tests, CI Thread Sanitizer gate,
   package smoke, realtime callback audit, and release gates pass on the exact
   release revision.
4. Performance evidence covers launch, main-thread work, steady-state CPU,
   memory, energy, wakeups, route churn, realtime callback deadlines, and
   shutdown.
5. At least 29 of 30 controlled cold launches become genuinely interactive
   before the Dock icon settles. The p95 interaction point must lead settlement
   by at least 150 ms.
6. The signed and notarized candidate passes Gatekeeper and upgrade testing.
7. The exact candidate passes physical Wave Link 3.2.2 and Stream Deck Plus
   testing on the connected Mac mini.
8. The release tag identifies the exact published `origin/main` revision.
9. GitHub, the live appcast, the website download, and Homebrew all identify and
   serve the same 1.7.1 build 19 artifact.
10. The Half Bounce recording and post copy are ready for Jonathan's approval.

## Non-goals

- No new product feature.
- No visual redesign.
- No control protocol change.
- No bundle identifier, signing identity, Sparkle key, or minimum macOS change.
- No public social post without Jonathan's approval of the final media and copy.
- No release shortcut that replaces missing physical hardware evidence with a
  waiver.

## Chosen approach

Use one measured integration release. Establish current security and
performance baselines first, repair the pull requests in dependency order, run
deep audits on the combined code, and release one exact candidate.

Directly merging all existing pull requests would combine overlapping release
changes and preserve several incomplete fixes. Ignoring every pull request and
starting over would discard useful tests and duplicate valid analysis. The
integration approach retains sound ideas while making the combined behavior the
unit of review.

## Work sequence

### 1. Baseline and measurement harness

Record the exact source revision and run the existing test suite before code
changes. Add privacy-safe launch milestones around work that can delay the first
frame or first successful control:

- synchronous store construction and persisted-state decoding;
- first main window frame and first menu item;
- backend start and initial snapshot;
- restored-route work;
- first row that can complete a mute or volume command;
- diagnostics, authorization, output-device inventory, and observer setup.

The measurement code must not log app names, device names, audio content,
profile names, or persisted values. Realtime callbacks must remain free of
logging, allocation, locks, dispatch, and async work.

Capture a comparable 1.7.0 baseline before changing the startup path. Run the
same scenarios on 1.7.1 and retain machine, OS, route-count, preference, and
artifact identity with each result.

### 2. Pull-request adjudication

Treat every branch as an untrusted proposal. Preserve each valid security goal,
but accept code only after current tests reproduce the issue and the repaired
behavior passes on the combined branch.

| PR | Planned disposition |

| #29 | Close as superseded because `main` already resolves Sparkle 2.9.5. |
| #34 and #42 | Replace with one publication-authority change. Require the release tag to equal current `HEAD` and `origin/main`, pin canonical SSH key material, and retain positive and negative provenance tests. |
| #35 | Redesign. Hash sealed staging before publication, keep kit and anchor failure recoverable, and test race and rollback paths. |
| #36 | Redesign. Preserve the 250 ms application-termination bound and prevent stranded Core Audio work without an unbounded quit. |
| #37 | Complete URL provenance through profile application and every Wave Link route path. Add volume, mute, and profile denial tests. |
| #38 and #39 | Combine the private writable-DMG directory with a unique volume token derived from that directory. Test normal and failure cleanup. |
| #40 | Reproduce the handshake reset, make listener self-proof nonblocking, and prove saturated-backlog startup remains prompt and fail-closed. |
| #41 | Canonicalize staging safely, require a real private directory, define the returned-path contract, and cover `/var` versus `/private/var`. |

After the replacements land, close superseded pull requests with concise
evidence that points to the integrated tests or commit.

### 3. Deep security audit

Audit the final combined design, not only individual diffs. The review covers:

- Core Audio object sizes, buffer geometry, integer conversion, ownership,
  teardown, callback lifetime, and resource exhaustion;
- the `waves://` parser, rate limits, provenance, profile application, and every
  route that can reach Wave Link;
- the same-user Unix socket, framing, admission budgets, peer identity,
  listener publication, timeouts, backpressure, and shutdown;
- Wave Link discovery, code-signature verification, loopback transport,
  protocol bounds, read-back checks, and fail-closed behavior;
- persisted JSON size and schema limits, private permissions, symlink handling,
  diagnostics redaction, and untrusted display strings;
- updater behavior, Sparkle keys and helper boundaries;
- build inputs, temporary paths, Git and tag authority, evidence sealing,
  notarization, GitHub Actions permissions, and publication provenance;
- dependency and secret scanning across tracked source and release artifacts.

Each validated finding receives a severity, proof, affected path, regression
test, fix, and verification receipt. False positives receive a concrete reason.

### 4. Startup and Half Bounce work

Waves currently renders an early mixer but disables the whole mixer until audio
startup completes. The startup path also performs route restoration,
diagnostics, authorization reads, output-device enumeration, persistence, and
observer setup before declaring the store running.

Change the readiness model only where measurement proves delay:

- keep route-ownership and controller-setting order intact;
- move diagnostics and inventory work that is not required for the first
  control out of the readiness path;
- parallelize only independent work with explicit ownership and cancellation;
- expose readiness per route when a global lockout is unnecessary;
- never present a control as successful before the backend confirms it;
- retain truthful warming and failure states for routes that are not ready.

The qualifying interaction is a completed volume or mute change on a real
running audio app in the signed, installed candidate with normal returning-user
state. A painted window, movable slider, queued command, hidden loading state,
or manipulated Dock animation does not count.

Run 30 cold-launch recordings under the same conditions. For each launch,
record process start, first frame, Dock settlement, attempted interaction, and
backend-confirmed completion. Require 29 passes and 150 ms p95 headroom. Submit
the selected clean recording to Bounce Lab and retain its report URL.

### 5. Whole-app performance and maintenance

Use comparable 1.7.0 and 1.7.1 scenarios:

- no routes, hidden window;
- one and ten managed routes, hidden window;
- menu panel open;
- main window foreground, background, and occluded;
- adaptive mixing and EQ combinations;
- repeated route creation, app launch and exit, device change, and recovery;
- callback stress across supported sample rates, channel layouts, and buffer
  sizes;
- clean and degraded shutdown.

Measure CPU, wakeups, energy, resident memory, dirty memory, threads, file
descriptors, retained controllers, callback duration against buffer deadline,
and audio overload or dropout signals. Run a short scenario matrix and a longer
candidate soak. Investigate any monotonic growth, deadline miss, audio glitch,
or comparable CPU or memory regression of 5 percent or more.

Maintenance includes dependency review, warnings, stale documentation, dead
code proven unreachable, formatting, release metadata, changelog, and cask
metadata. Mechanical cleanup must not widen the release into a refactor.

### 6. Verification and release

Run focused tests after each change. Before candidate construction, run the full
shared quality gate and the deep security verification again. Push the branch,
open the release pull request, and require green hosted checks before merge.

Build the exact clean `origin/main` revision as 1.7.1 build 19. Sign it with the
pinned Developer ID identity, notarize it through the existing Keychain
profile, staple it, verify Gatekeeper, verify the universal slices and dSYM, and
seal the candidate evidence.

Do not use either existing Mac mini checkout as release source. One is heavily
diverged, and the other is an older Wave Link test worktree. Transfer the sealed
candidate and a package from the private `JonathanRReed/waves-streamdeck`
repository to the Mac mini through the supported handoff kit.

On Mac mini, verify both launch orders, claimed and unclaimed apps, mixed
output, device changes, relaunch, route arbitration cycles, Stream Deck dial
changes, mute synchronization, and automatic recovery. Finalize the remote
receipt only from the exact candidate hashes.

After the public gate passes, create the signed release tag at the exact
`origin/main` revision, publish all GitHub assets, update and deploy the appcast
and website, update Homebrew, and fetch every public surface without cache.
Compare hashes so the public DMG is byte-for-byte the sealed candidate.

## Failure handling

- A failing baseline test stops implementation until the failure is understood.
- A security proposal that weakens availability, rollback, or fail-closed
  behavior is rejected even if its focused test passes.
- A performance change is reverted if it makes audio correctness or route
  ownership ambiguous.
- A candidate change after signing invalidates all candidate, hardware, and
  publication receipts.
- Missing remote hardware evidence stops publication.
- A mismatch between GitHub, appcast, website, Homebrew, or the sealed hash is a
  release failure, not a documentation issue.

## Evidence artifacts

The release keeps:

- the task contract and append-only decision log under `.audit/`;
- baseline and candidate performance reports with exact artifact identity;
- security findings and the final scan receipt;
- focused and full test output summaries;
- candidate, notarization, Gatekeeper, dSYM, and checksum evidence;
- the finalized Mac mini Elgato receipt;
- uncached public distribution verification;
- the Bounce Lab report and final approved media.
