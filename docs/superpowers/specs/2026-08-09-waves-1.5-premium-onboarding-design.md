# Waves 1.5 Premium Onboarding and Install Experience

## Status

Proposed for user review on 2026-08-09. Implementation must not begin until
this written design is approved.

## Objective

Make installing and learning Waves feel comparable to a polished first-party
macOS utility while getting people to a working mixer quickly.

The experience must:

- make the drag-to-Applications installation step obvious;
- explain required macOS access before asking for it;
- diagnose readiness problems without presenting a wall of healthy checks;
- get a ready user into the real mixer in under one minute;
- teach core controls in the real product rather than a simulated slideshow;
- let the user end the optional tutorial immediately;
- remain replayable from Help and Setup & Repair;
- avoid forcing existing users through first-run setup again; and
- preserve Waves' native, quiet, and precise product character.

## Product Principles

### First value before customization

The required path contains only the decisions needed for Waves to manage audio.
Appearance, launch behavior, shortcuts, menu-bar visibility, adaptive-mix
preferences, and other personal choices remain in Settings. Waves starts with
safe defaults instead of asking users to configure the product before they have
used it.

### Required setup and product education are separate

Permission and audio readiness can block the product honestly. A feature tour
cannot. The required setup therefore ends as soon as Waves is ready, while the
guided tour is a separate, optional layer over the real mixer.

### One clear action per state

Each screen has one primary action. Secondary actions never compete visually.
The permission preflight uses a single Continue action before macOS presents
protected system UI. Repair states use one specific action such as Open System
Settings, Choose Output, or Check Again.

### Truthful and contextual

Waves never claims to control monitor-only, yielded, unsupported, or unhealthy
routes. Tutorial callouts use the same route-capability policy and accessibility
semantics as the production mixer. If the requested action is unavailable, the
tutorial explains why and offers Skip Step or End Tour.

### Optional means immediately optional

Every optional-tour state includes End Tour. Escape performs the same action.
Ending the tour removes all overlays immediately, leaves the mixer usable, and
records the dismissal so Waves does not prompt again automatically for the same
experience version. The tour remains manually replayable.

## End-to-End Journey

### 1. Install from the disk image

The Waves DMG opens as an intentional Finder window, not a default directory
listing.

The layout is deterministic:

- a 660 by 430 point Finder window;
- a 1320 by 860 pixel two-scale background using the current Waves palette;
- the Waves app icon at the left and Applications at the right;
- a restrained directional mark and the text `Drag Waves to Applications`;
- 128 point icons with names visible;
- icon view with the sidebar, toolbar, status bar, and path bar hidden; and
- no visible files other than Waves and Applications.

The image must work in light and dark desktop environments without relying on
transparency for legibility. It uses the existing app icon and design tokens. It
does not include an installer package, license interstitial, separate launcher,
or decorative marketing carousel.

The package builder creates the background and Finder metadata deterministically.
The package verifier allows only the app, Applications link, background asset,
and Finder metadata, verifies their types and paths without following links,
and rejects extra visible or executable content.

If Waves launches from a mounted disk image or another read-only location, the
app presents a small installation advisory before setup. It offers Open This
Disk Image in Finder and Continue for Now. Waves never silently moves or copies
itself, and this advisory never claims installation succeeded.

### 2. Welcome

The first in-app surface is a compact, centered setup window using the real
Waves shell and app icon. It contains:

- title: `Your Mac, mixed around you`;
- supporting copy explaining that Waves gives each compatible app its own
  volume, mute, output, and sound controls;
- a local-processing note; and
- primary action: `Set Up Waves`.

The window has a stable minimum size and no large unused lower region. It does
not show progress dots before the user begins and does not expose preferences.

### 3. Audio Capture access

If Audio Capture is already authorized, Waves omits this step.

Otherwise, Waves explains why access is needed immediately before the native
request. The preflight has one button named Continue. It does not use Allow,
because only macOS grants the permission.

After Continue:

- if macOS can present the native request, Waves requests access once;
- if manual action is required, Waves opens the exact Privacy & Security pane;
- while waiting, the surface shows `Waiting for macOS` and checks again when
  Waves becomes active;
- denial or revocation shows concise repair instructions plus Open System
  Settings and Check Again; and
- all wording states that Waves processes audio locally and does not record or
  upload it.

There is no Skip action on this required permission preflight. Closing the
window quits setup without marking it complete. Relaunch resumes at the same
required state.

### 4. Readiness

After permission succeeds, Waves evaluates the existing readiness model for
capture authorization, compatible output, backend health, and routing support.

The normal case appears as a brief animated transition rather than four green
checklist rows. When all required checks pass, it advances automatically after
the state has remained stable long enough to avoid flicker.

Only problems remain on screen. Each problem includes:

- a plain-language title;
- one sentence explaining impact;
- one primary repair action;
- an optional technical disclosure for diagnostics; and
- live re-evaluation after the action or app activation.

Warnings that do not block core mixing are labeled `You can continue` and never
masquerade as failures. A degraded but usable backend can enter the mixer with
the same truthful limitation shown later in Setup & Repair.

### 5. Ready

The completion surface confirms actual readiness, not merely that buttons were
clicked.

It contains:

- title: `Waves is ready`;
- a short description of what was verified;
- primary action: `Start Mixing`; and
- secondary action: `Take the 60-Second Tour`.

Start Mixing completes required setup and opens the mixer immediately. Take the
Tour also completes required setup, opens the mixer, and begins the optional
tour. No preference choices are presented here.

### 6. Optional live mixer tour

The tour is a lightweight overlay and focus coordinator attached to the real
mixer. It never replaces the mixer with sample controls or writes tutorial-only
audio state.

The tour has at most four moments:

1. **Choose a sound** highlights one actionable, currently audible managed app.
2. **Set its level** asks the user to make one volume adjustment and confirms
   the real store transaction completed.
3. **Mute and restore** asks for mute followed by unmute, preserving the user's
   original state when the moment ends.
4. **Go further** identifies app details, EQ or output controls, Profiles, and
   Settings without requiring durable preference changes.

The tour chrome always shows the current moment, a short instruction, End Tour,
and where useful Skip Step. It does not cover the target control, capture
keyboard focus unexpectedly, or block unrelated mixer interaction. Escape ends
the tour. VoiceOver exposes the moment as an announcement and moves focus only
when the user starts or advances the tour.

If no actionable app is available, Waves does not ask the user to manufacture
activity or play bundled audio. It opens the mixer, marks the tour as deferred,
and offers one contextual `Show me how` tip when an eligible app later appears.
The user can dismiss that tip permanently for the current experience version.

If a route becomes unavailable during a moment, the overlay explains the
actual route state and offers Skip Step or End Tour. It never retries a control
mutation automatically.

### 7. Existing users and What's New

An upgrade from a profile that already completed guided setup never reopens the
required setup window.

The first main-window appearance on 1.5 can show one dismissible What's New card
summarizing the new mixer, routing-health, automation, and accessibility work.
Its actions are Take the Tour and Not Now. It is nonmodal, does not cover mixer
controls, and disappears immediately after either action.

What's New remains available from Help after dismissal. Setup & Repair provides
Run Guided Setup and Take the Mixer Tour as separate actions so users do not
need to revisit permissions merely to learn the interface.

## State Model and Migration

The existing schema-1 preferences envelope remains authoritative. New fields
are additive and default safely when missing.

The durable state is represented by explicit experience versions rather than
one ambiguous completion boolean:

- `requiredSetupVersion`: highest required setup experience completed;
- `guidedTourCompletedVersion`: highest tour completed;
- `guidedTourDismissedVersion`: highest tour explicitly ended or declined;
- `whatsNewDismissedVersion`: highest What's New card dismissed; and
- `deferredTourVersion`: tour waiting for an actionable managed app.

Version `1` represents the Waves 1.5 experience.

Migration rules are deterministic:

- a new install starts with every version at zero;
- an existing profile with `hasCompletedPrivacySetup == true` and
  `hasCompletedGuidedSetup == true` sets `requiredSetupVersion` to 1 and does
  not replay first-run setup;
- an existing completed profile leaves the tour and What's New versions at
  zero so the nonmodal 1.5 introduction can be offered once;
- an incomplete legacy profile remains incomplete and resumes the corresponding
  required permission or readiness state;
- manually running guided setup never clears valid permission state; and
- resetting tutorial state never changes audio, profiles, shortcuts, outputs,
  login-item behavior, or other preferences.

Legacy booleans remain decodable for 1.4.4 upgrades. Current saves write the
explicit version fields and preserve the schema-1 envelope.

## Architecture

### OnboardingLaunchPolicy

A pure, deterministic policy accepts preferences, permission state, readiness,
install location, and current experience version. It returns exactly one launch
surface or optional prompt. It owns no UI and performs no mutations.

### GuidedSetupCoordinator

A main-actor coordinator owns required setup phase, bounded readiness
observation, cancellation, and completion output. AppStore remains the
observable mutation facade. The coordinator never requests permission or opens
System Settings until the user invokes the current primary action.

### GuidedMixerTourCoordinator

A separate main-actor coordinator owns optional-tour moments, selected runtime
app identity, expected user action, accessibility announcement, and
cancellation. It consumes typed mixer transaction results and route capability.
It cannot bypass AppStore intent generation or write directly to the backend.

### InstallLocationAdvisor

A small read-only policy classifies the live bundle location as Applications,
mounted disk image, read-only external location, or ordinary writable location.
It supplies truthful presentation data only. It never moves, deletes, or opens
anything without an explicit user action.

### Focused views

`OnboardingView` remains the setup composition root and is split into focused
welcome, permission, readiness, and ready surfaces. Tour chrome is attached to
the mixer through one modifier or overlay boundary. Setup & Repair and Help
consume the same typed launch actions rather than duplicating state mutation.

## Data and Event Flow

1. App launch reads preferences and current backend facts.
2. `OnboardingLaunchPolicy` chooses installation advisory, required setup,
   ordinary mixer, or optional What's New prompt.
3. Required setup actions flow from a focused surface into
   `GuidedSetupCoordinator`, then through existing AppStore or system-settings
   boundaries.
4. Completion persists the explicit required setup version through the existing
   persistence coordinator before the mixer becomes the durable launch state.
5. Starting the tour selects an actionable app from the current authoritative
   session and creates a typed moment.
6. Real mixer actions continue through AppStore. The tour observes successful
   typed results and advances without owning the mutation.
7. End Tour cancels observation, clears overlays and temporary focus, persists
   dismissal, and leaves all product work owned by AppStore untouched.
8. Shutdown drains setup and tour observation tasks through the existing
   aggregate lifecycle contract.

## Error Handling and Safety

- Permission requests are user initiated and never loop automatically.
- System Settings links are derived from the existing typed destinations.
- Readiness polling is bounded, cancellable, and app-activation aware.
- Setup completion is not recorded until persistence succeeds. A save failure
  leaves the user in a usable session and reports that setup may reappear.
- Tour progression requires a successful real transaction, not a local control
  animation.
- A stale app identity, yielded route, or failed transaction cannot advance a
  moment.
- Ending or closing the tour is idempotent.
- App termination, relaunch, or shutdown cannot leave an overlay, hotkey
  suspension, retained task, or temporary mute behind.
- The DMG builder never modifies the source checkout and verifies every staged
  input before publication.

## Visual and Interaction Direction

The setup uses the existing Waves palette, typography, corner radii, and
materials. Premium means confident hierarchy, precise spacing, clear progress,
and restrained motion. It does not mean gradients on every surface, oversized
marketing copy, glass stacked inside glass, or a custom imitation of macOS
permission dialogs.

Motion uses short opacity and positional transitions. Reduce Motion removes
positional travel and uses immediate or cross-fade state changes. Reduce
Transparency uses opaque design-system fills. Increase Contrast preserves every
boundary and status without depending on color.

Every actionable control has a visible keyboard focus state. Back and Continue
follow normal tab order. Escape ends only optional education, never silently
marks required setup complete. All status meaning is available as text, label,
value, and help.

## Documentation and Release Integration

The implementation updates:

- README installation and first-run guidance;
- Help topics for setup, tour replay, permission repair, and installation;
- Product and Design documentation with the required-versus-optional model;
- release packaging documentation and package allowlists;
- the 1.5 plan with implementation and rendered-verification receipts; and
- the Elgato handoff so a clean remote machine follows the exact DMG and setup
  path before hardware testing.

The onboarding work changes no version, build number, bundle identifier,
protocol-v1 wire shape, audio routing authority, Sparkle key, or signing policy.

## Verification

### Deterministic model tests

- every launch-policy combination returns the correct surface;
- new, upgraded-complete, upgraded-incomplete, dismissed, replayed, and deferred
  states migrate correctly;
- missing additive fields decode safely from a raw 1.4.4 fixture;
- permission and readiness transitions never mark completion early;
- End Tour and Escape are idempotent from every optional moment;
- transaction failure, stale app, yielded route, and app exit do not advance;
- no actionable app produces one bounded deferred tip; and
- shutdown drains every coordinator-owned task.

### Hosted interaction and accessibility tests

- keyboard-only setup, repair, replay, and tour exit;
- VoiceOver labels, values, help, announcements, and focus order;
- Reduce Motion, Reduce Transparency, and Increase Contrast;
- full and compact mixer tour anchors;
- permission denied, permission already granted, no output, degraded backend,
  monitor-only, yielded, recovery, and empty mixer states; and
- What's New dismissal without blocking mixer controls.

### Rendered visual matrix

Render and inspect every setup stage, actionable repair state, ready state,
What's New card, and tour moment in Waves and Graphite palettes, light and dark
appearance, plus the accessibility combinations. Render the DMG background and
an actual mounted Finder window at the supported display scale. Evidence must
assert nonempty image output and record hashes.

### Package and installed-artifact tests

- verify the DMG allowlist, paths, link targets, Finder metadata, background,
  app identity, and absence of extra executable content;
- mount the exact built DMG and inspect the real Finder layout;
- launch once from the mounted image and verify the truthful advisory;
- copy to Applications and verify the advisory disappears;
- exercise clean consent, denied consent, existing consent, relaunch, and
  upgrade from the preserved 1.4.4 state; and
- repeat package, signing, notarization, stapling, Gatekeeper, update, and
  rollback checks on the final candidate after all onboarding changes land.

## Acceptance Criteria

The feature is complete only when all of the following are true:

1. A clean user can understand the DMG action without external instructions.
2. A ready user reaches the real mixer with no preference questionnaire.
3. Required permission copy precedes the native request and reports the actual
   resulting state.
4. Healthy readiness is brief; only actionable problems persist.
5. Start Mixing opens the product immediately.
6. The optional tour uses real mixer controls and can be ended instantly by
   button or Escape from every moment.
7. No eligible app results in a usable mixer and one dismissible deferred tip,
   not a blocked tutorial.
8. Existing completed users do not repeat required setup.
9. Guided setup, tour, and What's New remain separately replayable or
   dismissible.
10. Schema-1 upgrades preserve all 1.4.4 settings and state.
11. Rendered, accessibility, package, installed-artifact, and lifecycle evidence
    covers the production paths rather than helper-only substitutes.
12. The final signed and notarized 1.5.0 build 13 candidate repeats the exact
    install and onboarding journey before remote Elgato testing.

## Non-Goals

- no account creation, analytics, cloud tutorial state, or marketing signup;
- no bundled sample audio or automatic media playback;
- no installer package or privileged helper;
- no automatic app relocation or deletion of the mounted image;
- no forced feature tour for new or existing users;
- no redesign of audio routing, Wave Link arbitration, profiles, EQ, or
  external-control protocol; and
- no public release before the existing remote Wave Link and Stream Deck gate.
