# Waves 1.7.1 security finding dispositions

Scan `bedd5c5b-48d1-450d-a983-fc0245ed57ec` was sealed once on Mac mini against
exact source `3f70ce721b17149d85c82b010fcc85897cb7c6cf`. It reported 21
findings: 3 high, 7 medium, 11 low. Coverage was static only. Runtime,
external services and hardware were not exercised. The canonical report stays
on Mac mini; this file records each finding's title and its disposition for
1.7.1 build 19. Titles were transcribed from the remote command output.

"This batch" is commits `427ec7d`, `be17a9a` and `4f03d99` on
`codex/waves-1.7.1`.

A disposition of "fixed" means a failing regression reproduced the finding,
the repair made it pass, an independent read-only reviewer found no bypass,
and the full local test phase passed afterwards. "Accepted" and "deferred"
findings are open. Nothing below claims physical-hardware or signed-candidate
verification.

## Findings 1 and 2: signing trust model

`docs/RELEASE.md` deliberately keeps Developer ID signing and notarization on
the maintainer's Mac and out of hosted CI. Both findings describe what hostile
code already running as that maintainer account could do between a clean
source check and signing. Resisting that attacker needs a separately protected
signer, a trusted launcher outside the candidate revision and credential access
only inside that boundary. That is a design change, not a maintenance fix.

Codex asked Jonathan on September 5 whether to keep the existing model for
1.7.1. His next instruction was "Finish up and publish." This batch treats that
as keeping the documented model for 1.7.1 and records the separate-signer design
as post-1.7.1 work. Jonathan has not answered the question in so many words. If
he wants the stricter model before 1.7.1 ships, the release should wait for it.

## Finding 7: connected-peer identity

Discovery verifies the Wave Link listener's PID and Elgato designated
requirement before Waves connects. The residual window is a local process
running as the same user that rebinds the loopback port between that check and
the connect. `URLSessionWebSocketTask` does not expose the live local endpoint
needed to tie the connection to the verified process, so a complete fix
replaces the private socket transport with Network.framework and compares the
kernel's peer tuple, process lifetime and signature before any command. The
design is recorded in the release-publication tracker. It changes transport
architecture and needs Wave Link 3.2.2 hardware verification, so it is deferred
past this maintenance release.

## Findings 5, 6, 8, 9, 10, 13, 16 and 17: release tooling

These describe trust boundaries inside the release pipeline: receipt
authentication, gate self-assertion, tag-key provenance, inherited tool
environments, notary-log binding, evidence collection and diagnostic
disclosure. None of that code ships in the app. Each runs only on the
maintainer's Macs, on inputs the maintainer supplies, so exploitation already
requires control of that account or those inputs. Each needs its own
source-backed repair with tests and an independent review, which is more than
this maintenance release should absorb. They are tracked for the next release.

## Finding 19: subscriber exhaustion

The control socket already enforces a peer-uid check, 8 total connections, 4
per process and 2 subscribers per process. Four cooperating same-user processes
can still hold every slot. The worst case is a local denial of the control
surface for that user, with no privilege or route change. A subscriber budget
across processes is a small follow-up; it is deferred rather than rushed into
the release.

## Finding 20: spoofed conferencing app

Automatic conferencing pause is an opt-in preference. The category comes from
the frontmost application's bundle identifier, so a masquerading app has to be
brought frontmost by the user before it can trigger a pause. The finding 4
repair already refuses control authority when different runtime identities
claim one logical app. Binding the conferencing category to a signed identity
is deferred to a later release.

## Review items outside the scan

Two PR review comments were confirmed and repaired in this batch: AppStore now
records the first-control confirmation event when the backend reports
`.noChange` because the route already matched, and the phase runner keeps its
timeout or interruption exit status when the kernel denies signal or process
group inspection, reporting cleanup it could not confirm. Two hosted socket
tests that failed under parallel load now use realistic setup budgets and
assert the behavior they were written for; production code did not change for
that repair.
