## Sanitizer diagnosis

The Waves harness compiled successfully in 35.52 seconds, then crashed with
SIGSEGV. The faulting stack starts in `__tsan::SlotLock`, `__tsan::Release`,
and `wrap_dispatch_once`, followed by dyld shared-cache enumeration and TSan
initialization. It contains no Waves scenario frames.

A minimal C program with no Waves dependencies, containing only `puts` and `return 0`, reproduced
the failure. A second run used an empty environment with explicit PATH and
`DEVELOPER_DIR=/Library/Developer/CommandLineTools` for compilation and execution.
Both variants compiled with exit 0. The plain executable printed its main-entry
message and exited 0. The `-fsanitize=thread` executable printed no main-entry
message and exited 139. Its crash report has the same first ten stack frames.

Environment: macOS 27.0 build 26A5425a, Apple clang 17.0.0
`clang-1700.6.3.2`. The Waves harness and clean C-probe crash reports both load
`/Library/Developer/CommandLineTools/usr/lib/clang/17/lib/darwin/libclang_rt.tsan_osx_dynamic.dylib`.

This localizes the failure to sanitizer initialization in this environment.
It does not distinguish a sanitizer bug from an OS/dyld/toolchain compatibility
issue. It is not a passing race check and does not prove Waves is race-free.
An independent read-only review by `tsan_failure_review`, GPT-5.6 Sol with low
reasoning, agreed with this classification and requested the clean-environment
transcript, which is now retained.

The minimal source and reproduction script are in
`/tmp/waves-tsan-probe.ZdP8oO/`. The first attempt to save a transcript stopped
on Bash's empty-array handling under `set -u`, before compiling the probe.
Removing that diagnostic-script option allowed the recorded clean-environment
comparison. No Waves source or sanitizer acceptance rule was changed.

Next proof: run the same probe with a supported full Xcode toolchain, then run
the unchanged Waves TSan gate. Full Xcode and `xctrace` are unavailable locally.
